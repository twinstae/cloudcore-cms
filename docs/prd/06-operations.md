# 운영 PRD: 프로비저닝·배포·백업

버전: v0.1 | 작성자(PM): | 최종 수정일: 2026-10-23 | 현재 완성도: 50

## 1. 가치 정의

김서연은 자기 Cloudflare 계정에 Cloudcore를 한 번 올려 두고, 새 버전이 나오면 GitHub에 반영된 코드가 자동으로 배포되게 한다. 그 결과 그녀는 서버를 관리하지 않고도 사이트를 계속 운영하고, 문제가 생겼을 때 무엇이 실패했는지 확인하고 데이터를 되살릴 수 있다.

## 2. 배경

Cloudcore는 SaaS가 아니라 self-hosted 도구다. 김서연이 자기 도메인, 자기 D1, 자기 R2를 소유한다. 따라서 처음 한 번의 준비 작업과, 이후의 배포·백업·관측을 그녀가 직접 한다. 이 PRD는 그 작업이 "무엇을 어떤 순서로 하면 되는지"를 정한다.

## 3. 맥락

- 배포는 Cloudflare GitHub 연동(Workers Builds)으로만 한다. GitHub Actions는 쓰지 않는다.
- 무료 플랜이 필수 조건이다(ADR-0005). 요청당 CPU 10ms, 하루 10만 요청, 계정 전체 동시 빌드 1개, 빌드 상한 20분이 운영의 전제다.
- 도메인은 Cloudflare Registrar에서 하나를 사서 `example.com`(Site), `admin.example.com`(API+Admin), `media.example.com`(R2)로 나눈다.
- 비밀값은 저장소에 두지 않고 Cloudflare 대시보드의 Worker 시크릿에 넣는다.
- D1과 R2는 Worker 바인딩으로 붙고, 환경(미리보기/운영)을 따로 두지 않는다. 사이트 하나에 환경 하나다. `[가정]`

## 4. 페르소나

김서연은 Cloudflare 대시보드에서 도메인과 D1을 만들어 본 경험이 한 번 있다. `wrangler` 명령을 복사해 붙여 넣을 수는 있지만, 빌드 로그를 읽고 원인을 찾는 일은 어렵다. 그래서 그녀는 "무엇을 눌러야 하는지"가 순서대로 적힌 체크리스트를 원한다.

## 5. 메인 시나리오

김서연은 도메인을 사고 GitHub 저장소를 자기 계정으로 fork한다. Cloudflare 대시보드에서 D1 데이터베이스와 R2 버킷, Images를 만든 뒤, 안내된 `wrangler d1 migrations apply` 명령으로 스키마를 만든다.

그녀는 `admin` Worker에 저장소를 연결하고, 빌드 설정에 root directory와 빌드 명령을 넣는다. 시크릿 목록(Better Auth secret, Deploy Hook URL 등)을 하나씩 붙여 넣는다. 첫 배포가 끝나면 `admin.example.com/api/setup`에서 Owner 계정을 만든다.

Site는 정적 자산만 있는 Worker로 배포하고, Deploy Hook을 만들어 API 시크릿에 넣는다. 세 도메인을 각각 연결하고 나서, 그녀는 글을 하나 발행해 Site에 나타나는지 확인한다.

몇 달 뒤 무료 한도 알림을 받으면, 그녀는 Admin에서 마지막 빌드 시각과 실패 여부를 확인하고, 필요하면 백업 파일을 내려받는다.

## 6. 사용자 여정 (one-way)

도메인 구입 → 저장소 fork → D1/R2/Images 생성 → 마이그레이션 → Worker 연결·시크릿 입력 → 첫 배포 → Owner 설정 → Site Worker와 Deploy Hook → 도메인 3개 연결 → 첫 글 발행 확인 → (주기적으로) 로그·한도·백업 확인

## 7. 유즈 케이스

### UC-O01 처음 한 번 인프라를 준비할 수 있다
- 시작 조건: 김서연이 Cloudflare 계정과 도메인을 가지고 있다.
- 사용자 행위: 김서연은 체크리스트를 따라 D1, R2, Images를 만들고 마이그레이션을 적용할 수 있다.
- 결과/정책: 체크리스트는 각 단계에서 대시보드의 어느 메뉴를 누르는지와, 만든 리소스 이름을 어디에 적어 두는지를 알려 준다. 순서를 건너뛰면 다음 단계가 실패하는 이유도 함께 적는다.
- 관련 시나리오 구간: 인프라 준비.

### UC-O02 Worker를 배포하고 시크릿을 넣을 수 있다
- 시작 조건: 저장소가 GitHub에 있다.
- 사용자 행위: 김서연은 `admin` Worker에 저장소를 연결하고, 필요한 시크릿을 넣고, 배포 결과를 확인할 수 있다.
- 결과/정책: 시크릿 이름과 용도가 표로 정리되어 있고, 값은 저장소나 문서에 남기지 않는다. 배포가 실패하면 빌드 로그에서 실패한 단계가 보인다.
- 관련 시나리오 구간: Worker 연결 → 첫 배포.

### UC-O03 세 도메인을 연결할 수 있다
- 시작 조건: Worker가 배포되어 있다.
- 사용자 행위: 김서연은 Site, Admin, Media 각 도메인을 해당 Worker나 버킷에 연결할 수 있다.
- 결과/정책: Admin과 API는 같은 도메인을 쓴다. Media는 R2 커스텀 도메인으로 서빙한다. 연결 후 사이트 간 링크가 모두 동작한다.
- 관련 시나리오 구간: 도메인 연결.

### UC-O04 코드를 바꾸면 자동으로 배포된다
- 시작 조건: 김서연이 저장소의 기본 브랜치에 커밋을 올렸다.
- 사용자 행위: 김서연은 별도 조작 없이 새 버전이 배포되기를 기대할 수 있다.
- 결과/정책: Worker 빌드가 성공해야 배포된다. 스키마 변경이 있으면 마이그레이션 파일을 먼저 적용해야 한다는 안내가 릴리스 노트에 있다.
- 관련 시나리오 구간: 새 버전.

### UC-O05 백업을 내려받고 복원할 수 있다
- 시작 조건: 김서연이 Owner로 로그인했다.
- 사용자 행위: 김서연은 Admin에서 Content 전체를 JSON으로 내려받을 수 있다. 운영자는 D1 export와 R2 동기화 명령을 실행할 수 있다.
- 결과/정책: JSON에는 Content, Tag, Site Settings, Revision이 들어가고 Media 파일 자체는 URL로만 참조한다. 복원 절차는 문서에 명령으로 적혀 있다. `[확인 필요]` 1차 범위에 복원 도구까지 넣을지.
- 관련 시나리오 구간: 백업.

### UC-O06 한도와 장애를 확인할 수 있다
- 시작 조건: 사이트가 운영 중이다.
- 사용자 행위: 김서연은 Cloudflare 대시보드에서 요청 수, CPU 시간, 빌드 사용량을 확인할 수 있다.
- 결과/정책: 어느 지표가 한도에 가까워지면 무엇을 줄일 수 있는지가 문서에 적혀 있다. 로그인 요청의 CPU 시간은 배포 후 한 번 실측해 기록한다.
- 관련 시나리오 구간: 한도 확인.

## 10. 열린 질문과 결정 기록

- `[확인 필요]` JSON export를 1차 범위에 넣을지, 넣는다면 복원 도구까지 만들지.
- `[확인 필요]` 관리자 화면의 "빌드 상태"를 어디까지 노출할지(Site Settings vs 별도 화면).
- `[확인 필요]` `wrangler` 버전과 Node/bun 버전을 문서에 고정할지.
- 결정: 배포는 Workers Builds만, GitHub Actions 없음(map, ADR).
- 결정: 무료 플랜 한도 안에서 설계(ADR-0005).
- 결정: 도메인 3개 구성(ADR-0003).
- 결정: 첫 배포 후 로그인 CPU time을 실측해 PBKDF2 반복 횟수를 맞춘다(티켓 16, 23).
